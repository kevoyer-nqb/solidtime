Build the complete notification system: database schema, base notification classes with preference-aware email delivery, API endpoints for listing/reading/counting notifications, notification bell UI with polling in AppLayout, and notification preferences UI in member settings.

Purpose: Every downstream feature (approvals, budgets, PTO, etc.) needs to send notifications. This plan delivers the infrastructure they all depend on -- built once, used everywhere.
Output: Working notification bell in the app header, preference management UI, and a BaseNotification class that any feature can extend to send notifications.
</objective>

    **Migrations:**
    1. Create `notifications` table migration. Use Laravel's notification table structure but with `$table->uuid('id')->primary()` and `$table->uuidMorphs('notifiable')` (NOT `$table->morphs()` -- solidtime uses UUIDs). Include `type`, `data` (text), `read_at` (nullable timestamp), `created_at`, `updated_at`. Add composite index on `(notifiable_id, notifiable_type, read_at)` for unread count performance.
    2. Create `notification_preferences` table migration: `uuid id PK`, `foreignUuid member_id` constrained to `members` with cascadeOnDelete, `string notification_type`, `boolean email_enabled default false`, `timestamps`. Add unique constraint on `(member_id, notification_type)`.

    **Enums:**
    3. Create `NotificationType` enum (backed string enum). Start with a single `Test = 'test'` type for infrastructure testing. Add method `isDefaultEnabled(): bool` that returns `false` for `test`. Per user decision: critical notifications (approval-related, budget alerts) default enabled; informational default disabled. Feature phases will add their types. Add method `label(): string` returning human-readable name. Add method `category(): string` returning 'critical' or 'informational' for grouping in the preferences UI.
    4. Create `NotificationChannel` enum with values `Database = 'database'` and `Mail = 'mail'` for future extensibility.

    **Model:**
    5. Create `NotificationPreference` model with `HasUuids` and `CustomAuditable` traits (matching existing model conventions). Define `fillable`: `member_id`, `notification_type`, `email_enabled`. Add `member()` belongsTo relationship. Add scope `forMember(string $memberId)` and `forType(NotificationType $type)`.

    **Base Notification:**
    6. Create `app/Notifications/BaseNotification.php` as abstract class extending `Illuminate\Notifications\Notification` implementing `ShouldQueue`. Use `Queueable` trait. Define abstract methods: `getNotificationType(): NotificationType`, `getOrganizationId(): string`, `getTitle(): string`, `getBody(): string`, `getActionUrl(): string|null`.

    Implement `via(object $notifiable): array` method:
    - Always include `'database'` channel
    - Check `shouldSendEmail($notifiable)` -- if true, add `'mail'` channel
    - Per user decision: instant delivery only, one email per event, no batching

    Implement `shouldSendEmail(object $notifiable): bool`:
    - Look up the Member for this User + Organization combination
    - Query `NotificationPreference` for that member_id + notification_type
    - If no record exists, fall back to `$this->getNotificationType()->isDefaultEnabled()`
    - If record exists, return `$preference->email_enabled`

    Implement `toArray(object $notifiable): array`:
    - Return `['organization_id' => $this->getOrganizationId(), 'type' => $this->getNotificationType()->value, 'title' => $this->getTitle(), 'body' => $this->getBody(), 'action_url' => $this->getActionUrl()]`

    Implement `toMail(object $notifiable): MailMessage`:
    - Use minimal Blade markdown template (matching existing `@component('mail::message')` pattern from codebase)
    - Subject: `$this->getTitle()`
    - Body: `$this->getBody()`
    - If `getActionUrl()` is not null, add action button

    **Service:**
    7. Create `NotificationService` with method `send(User $user, BaseNotification $notification): void` that calls `$user->notify($notification)`. This wrapper exists so future features have a single entry point (for potential future additions like rate limiting, logging). Keep it minimal now.

    **API Controller:**
    8. Create `NotificationController` extending the base `Controller` class (following existing pattern with `PermissionStore` injection):
    - `index(Organization $organization)`: check permission `notifications:view:own`, get auth user, query `$user->notifications()->where('data->organization_id', $organization->getKey())->orderBy('created_at', 'desc')->paginate(20)`, return JSON
    - `unreadCount(Organization $organization)`: check permission `notifications:view:own`, count `$user->unreadNotifications()` filtered by org, return `{count: N}`
    - `markAsRead(Organization $organization, string $notificationId)`: find notification on user, call `markAsRead()`, return `{success: true}`
    - `markAllAsRead(Organization $organization)`: update all unread for this org, return `{success: true}`

    9. Create `NotificationPreferenceController`:
    - `index(Organization $organization)`: get current member, return all NotificationType values with current preference for each (preference record OR default). Return array of `{type: string, label: string, category: string, email_enabled: bool}`.
    - `update(NotificationPreferenceUpdateRequest $request, Organization $organization)`: validate `notification_type` (must be valid enum), `email_enabled` (boolean). Use `updateOrCreate` on NotificationPreference for current member + type. Per user decision: member self-service only, no admin override.

    **Request Validation:**
    10. Create `NotificationIndexRequest` extending `BaseFormRequest` (if one exists, otherwise `FormRequest`). Minimal -- just authorize.
    11. Create `NotificationPreferenceUpdateRequest` with rules: `notification_type` required, string, must be valid NotificationType value; `email_enabled` required, boolean.

    **Routes:**
    12. Add notification routes to `routes/api.php` inside the existing organization-scoped group:
    ```
    Route::get('notifications', [NotificationController::class, 'index']);
    Route::get('notifications/unread-count', [NotificationController::class, 'unreadCount']);
    Route::post('notifications/{notification}/mark-as-read', [NotificationController::class, 'markAsRead']);
    Route::post('notifications/mark-all-as-read', [NotificationController::class, 'markAllAsRead']);
    Route::get('notification-preferences', [NotificationPreferenceController::class, 'index']);
    Route::put('notification-preferences', [NotificationPreferenceController::class, 'update']);
    ```

    **Permissions:**
    13. Add `'notifications:view:own'` and `'notification-preferences:manage:own'` to the existing `configurePermissions()` method in `JetstreamServiceProvider.php`. Grant to all roles (Owner, Admin, Manager, Employee) since every user manages their own notifications.

    **Tests:**
    14. Create `NotificationEndpointTest.php` following existing test patterns (extend `ApiEndpointTestAbstract` or `TestCaseWithDatabase`). Test:
    - `test_user_can_list_notifications_for_organization`: create test notification, assert it appears in list

    - `test_user_can_mark_notification_as_read`: mark one, verify read_at set
    - `test_user_can_mark_all_as_read`: verify all notifications for org marked
    - `test_notification_preferences_default_to_type_setting`: verify fallback
    - `test_user_can_update_notification_preference`: toggle email_enabled, verify stored

    15. Create `NotificationPreferenceFactory` for testing.
